## 1. Анализ вариантов миграции.

### 1.1. High-level Design

#### Преимущества:
- Быстрая миграция.
- Простота управления (нет параллельной работы двух систем).
- Явное завершение (либо работает, либо откат).
- Нет синхронизации данных (данные мигрируют один раз).

#### Ограничения:
- Высокий риск (потеря всех данных).
- Длительный downtime.
- Невозможно тестировать реальную нагрузку.
- Невозможно постепенное обучение.

**Не подходит:**
- Downtime недопустим (работа с пациентами).
- Потеря медицинских данных.
- Слишком высокий риск.

---

### 1.2. Parallel Run

#### Преимущества:
- Минимальный downtime (использование обеих систем одновременно).
- Возможность сравнения результатов.
- Возможность отката (старая система продолжает работать).
- Постепенное обучение.
- Тестирование на реальной нагрузке.
- Compliance (медицинская система всегда доступна для пациентов).

#### Ограничения:
- Сложность синхронизации (двойной учет данных).
- Высокие затраты.
- Долгий процесс.
- Риск несогласованности.
- Требует комплексного мониторинга обеих систем.

**Подходит:**
- Непрерывность обслуживания пациентов.
- Постепенное обучение команды.
- Минимизация риска потери данных.
- Возможность отката в любой момент.

---

### 1.3. Branch by Abstraction

#### Преимущества:
- Более управляемо чем Parallel Run.
- Лучшая тестируемость.
- Постепенное обучение команды.
- Возможность отката.
- Compliance (медицинская система всегда доступна для пациентов).

#### Ограничения:
- Архитектурная сложность (для создания хороших абстракций).
- Долгий процесс.
- Риск архитектурных ошибок.
- Сложность поддержки.

**Подходит частично:**
- Требуется экспертиза в архитектуринге.
- Очень долгая миграци.
- Команда не имеет опыта с архитектурой (HIGH RISK).

---

### Выбор: PARALLEL RUN

1. **Критичность системы:** Даунтайм недопустим для медицинского центра.
2. **Требования к надежности:** Потеря медицинских данных недопустима.
3. **Меньше требований к опыту:** В команде нет опыта с микросервисами, есть возможность учиться постепенно.
4. **Обеспечение качества:** Возможность сравнить результаты обеих систем.
5. **Адаптация к нагрузкам** Постепенное увеличение нагрузки на новую систему.

## 2. Ключевые риски

| Риск | Вероятность | Влияние | Митигация |
|-|-|-|-|
| **Потеря медицинских данных** | Низкая | Высокое | Дублирование систем полной миграции.<br>Ежедневные бэкапы. |
| **Неконсистентность между системами** | Средняя | Высокое | Мониторинг в режиме реального времени.<br> Алерты на ключевые показатели. |
| **Недоступность платежной системы** | Низкая | Высокое | Реализация запасного платежного шлюза. |
| **Повреждение данных при миграции** | Средняя | Высокое | Детализированное логгирование.<br>Dry run тестирование. |
| **Инфраструктура становится узким местом** | Высокая | Среднее | Нагрузочное тестирование перед запуском.<br>Реализация слоя кэширования.<br>Обеспечение горизонтального масштабирования. |
| **Трудности у команды при миграции** | Высокая | Низкое | Обучение команды.<br>Подключение внешнего эксперта. |
| **Несовместимость API лаборатории** | Низкая | Среднее | Обеспечение резервной ручной загрузки рехультатов.<br>Тестирование на реальных данных. |
| **Ошибки в работе приложения** | Высокая | Среднее | Разработать план отката.<br>Разработать мониторинг ключевых показателей системы. |

## 3. План действий на случай проблем

### 3.1. Деградация производительности

Задержка ответов новой системы > 1s или error rate > 5%.

- 5 мин: увеличить monitoring, проверить логи.
- 10 мин: уменьшить % трафика на новую систему.
- 15 мин: откат на предыдущий процент.
- 30 мин: полный откат на старую систем.

Ответственный: SRE инженер.

### 3.2. Неконсистентность данных между системами

Проверка несогласованности обнаружила > 100 несоответствий.

- Остановить двойную запись.
- Анализ корневых проблем.
- Ручное исправление данных при необходимости.
- Продолжить двойную запись.
- Мониторинг.

Ответственный: SRE инженер, DBA, ведущий разработчик.

### 3.3. Платежная система не авторизует платежи

Платежный сервис возвращает 403/500 ошибки.

- 2 мин: проверить доступность платежного шлюза.
- 4 мин: проверить настройки в Vault.
- 10 мин: fallback на резервный шлюз (1С).
- Дополнительные исследования проблем.
- Переключение обратно после восстановления.

Ответственный: SRE инженер, ведущий разработчик.

### 3.4. Ошибки в новой системе

- 2 мин: переключение трафика на старую систему (1С).
- 4 мин: остановка миграционных процессов.
- Анализ корневых проблем.
- Исправление ошибок.
- Восстановление объема трафика до переключения.
- Мониторинг.

Ответственный: ведущий разработчик.
